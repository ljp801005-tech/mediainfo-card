## v1.12.2

「好点了，但是还是卡」，而且「BDInfo 的页面特别明显」—— 上一版把「逐元素克隆」砍掉了，但**原盘页独有的两步无用功**还在，而且首屏那次扫描是同步抢主线程的。

**① 原盘页面每次重扫都在做两件毫无意义的事。** 面板反解（`htmlPanelInfos` → 整页 `querySelectorAll('div,section,…')` + 逐块读首个子元素）与 General 补捞（`grabGeneralBlock(readText(document.body))` → **整页克隆**）都是为了「站点把 MediaInfo 渲染成 Video/Audio/Subtitle 三栏、没有原文」这种情况准备的。原盘自带 `Disc Label / Disc Size / MPLS / Total Bitrate`，根本不存在「没有原文」，也永远不会有 `General` 段 —— 可这两步以前在 BDInfo 页上是每次重扫都跑：面板那步 2500 个节点的 `querySelectorAll` + 逐块 `normTxt`，General 那步一次全页 `cloneNode(true)`。现在只要候选里认出了 BDInfo，两步一起跳过。

**② 首屏扫描不再跟站点抢主线程。** 以前 `DOMContentLoaded` 一触发就同步 `scanAndRender(true)`：SSD 的详情页自己初始化（1323 行的评论表、图片、脚本）本来就要几百毫秒，我们再插一次整页扫描，体感就是「打开就卡」。现在等 `load` 之后、并且排到 `requestIdleCallback` 再跑（页面迟迟不 load 时 2.5 秒兜底），后面的补扫也一律走空闲时段。

**③ 卡片已经在，且原文没变 → 不重扫。** 记下上次识别成功时锚点节点的文本长度；观察器叫醒我们时，只要锚点还在原地、长度一样、距上次完整扫描不到 20 秒，就只做一次 `textContent.length` 判断直接返回。另外观察器不再「见到媒体关键词就扫」：新节点落在锚点里（站点重绘简介区）或文字已经在当前原文里（同一段被贴到推荐位 / 引用块），都不再触发。

**④ 诊断能直接看出卡在哪。** 新增两行：

```
扫描耗时: 最近一次 28ms（候选 9 / 面板 0 / General 0 / 解析 1 / 渲染 18） 累计 1 次，指纹跳过 3 次
主线程长任务: 2 次 / 合计 118ms / 最长 64ms（最近 3.2s 61ms、7.8s 57ms）
```

`主线程长任务` 用 `PerformanceObserver` 的 longtask 采集，长任务是谁造成的一眼能分清：如果是我们扫的那一下，`扫描耗时` 会同步变大；如果长任务出现在别的时间点，那是站点自己的脚本。

实测（仿 SSD 夹具：15k 元素、`table_details` 里放 BDInfo、每 40ms 插 3 个广告节点）：注入后 9 秒内扫描 **4 次 / 合计 82ms → 1 次 / 28ms**，BDInfo 页的面板 + General 两步从 4ms 降到 0；21k 元素（+1400 行评论表）版本 36ms，卡片仍是 10 行字段、内嵌落位正常。

## v1.12.1

「在 SSD 打开插件，网页特别卡，关掉就好了」—— 卡的不是渲染，是**扫描**。

一次 `scanAndRender()` 以前要做三件很贵的事：

1. **逐元素 `readText()`**：TreeWalker 走遍整页每个元素，每个都克隆一次子树（为了把 `<br>` / 块级元素补成换行）再跑一遍 `scoreMediaInfo()`。SSD 那种详情页元素上千、简介区几十 KB，光这一项就是几百毫秒级 —— 而且克隆出来的字符串还要再走一遍 `deRawNames()` / `deZhNames()` 的逐行循环。
2. **无条件扫整页**：`pageLabelScan()`（`readText(document.body)`，整页克隆 + 正则）每次重扫都跑，哪怕解析结果一个字段都不缺；`grabGeneralBlock(readText(document.body))` 同理。
3. **`collectRoots()` 重复全量查找**：一次扫描里被调用 3~4 次（候选收集、整页文本、`tightAnchor`、诊断），每次都 `querySelectorAll('*')` 遍历整页找 iframe / shadow root。

再叠上观察器：`MutationObserver` 只看「有没有新增元素」，站点弹幕、广告位、计时器每插一个节点就排一次全量重扫（450ms 防抖），页面一直在动 → 一直在扫 → 主线程喘不过气。

改动：

- 候选扫描改成**带剪枝的深度优先**：先取节点自己的 `textContent`（不克隆），不含媒体关键词（`SCAN_KEY`）就整棵子树跳过 —— 父节点没有关键词，子节点不可能有，剪枝是精确的；命中了才 `readText()` + 评分。`skipTag`（table / ul / img…）从「整棵跳过」改成「不当候选、但继续往下」，行为与老实现一致。
- `collectRoots()` 加一次扫描内的缓存，`scanAndRender()` 开头 `resetRoots()`。
- 整页标签兜底改成**按需**：只有解析出来的信息真的缺文件名 / 体积 / 日期时才 `pageLabelScan()`。
- 观察器两道闸：新节点里没有媒体关键词就不扫；两次扫描至少隔 1.5 秒，连续 3 次扑空后拉长到 6 秒（页面本来就不带 MediaInfo 时更省）。
- 顺手修短格式 BDInfo 的音轨重复：`Audio: English / DTS-HD Master Audio / …` 既命中「Key: value」（进 kv），又命中「段头直接带值」（进 `tables`），最后 `kv.concat(tables)` 就整条音轨两份 —— SSD 那份 5 条变 10 条。现在「段头带值」只负责换段，值交给 kv。

实测（Chrome headless + CDP，同一份仿 SSD 夹具：3000 个填充元素、`table_details` 里放短格式 BDInfo、每 40ms 插 3 个广告节点）：注入后 8 秒内长任务 **73ms → 0ms**，两次都渲染 10 行字段、内嵌落在 `tr` 上；音轨行 `@` 计数 11 → 6（5 条音轨 + 1 条视频码率），不再重复。

## v1.12.0

一晚上两份贴文，两种「文本明明在页面上，卡片就是不出」。

**① 引用框把「引用」和 `General` 粘成一行。** NexusPHP 的简介格是 `<fieldset><legend>引用</legend>General<br>Unique ID : …`，`textContent` 里第一行就是「引用General」（`legend` 不算块级元素，克隆时也不补换行）。评分里 `General` 那一条只认「行首就是 General」，于是 +3 拿不到，整块得分停在 **5**（门槛 6）；而 `Video / Audio / File size` 都正常命中，所以用户在诊断里看到的是「General 段头=false、得分 5、识别份数 0」—— 差 1 分，最难猜。现在 `General / Video` 的判分改用与解析同一套段头正则（允许「引用 / 引自 / 代码」前缀），`引用General` 与裸 `General` 同分。

**② 中文版 MediaInfo 导出的全中文标签。** 段头是 通用 / 视频 / 音频 / 文本 #1 / 菜单，字段是 完整名称 / 文件大小 / 总体码率 / 声道数 / 位深……，标签之间用全角空格 `\u3000` 对齐，名字里还夹全角字母与全角斜杠（`特征　ＩＤ`、`格式／信息`、`格式配置　（Ｐｒｏｆｉｌｅ）`）。原来一条英文标签都匹配不上，整块得分 **0**。新增 `deZhNames()` 只翻「标签侧」（与 `deRawNames()` 同一路数，可重复调用）：

- 段头：通用 → General、视频 → Video、文本 #N → Text #N、菜单 → Menu；
- 50 余个字段名按归一后的键查表（去全角空格、去「（Profile）」这类补充说明、全角转半角）；
- `格式／信息`、`编解码器　ＩＤ／信息` 这类解释性重复行整行丢弃，否则 `Format` 会被顶成「High Efficiency Video Coding」；
- 值侧只还原本地化写法：`1小时 3 分钟 → 1h 3min`、`57 分钟 9 秒 → 57min 9s`、`3 840 像素 → 3 840 pixels`、`6 声道 → 6 channels`、`10 位 → 10 bits`、`恒定码率 → Constant`、`逐行扫描 → Progressive`、`有损 → Lossy`、`是 / 否 → Yes / No`、`中文 (简体) → Chinese (Simplified)`（`英语 (English)` 这种重复括号直接丢掉英文）；认不出的标签原样保留，不猜。

两份文本都进了单测（引用前缀 9 条 / 中文界面 12 条），并用用户给的真实贴文核过：9.54 GiB · 1h 31min · 3840×2160 · H.265 @ 14.5 Mbps · DD+ Atmos 5.1；6.43 GiB · 1h 3min · 3840×1600 (2.40:1) · H.265 @ 13.8 Mbps · 10 bit · DD+ Atmos 5.1 · 4 条字幕。

**③ 扩展与脚本版本对齐。** 早期扩展输出到 `dist/mediainfo-card-extension/`，后来改成 `dist/extension/`，老目录一直躺在磁盘上（还停在 1.11.2）。手上加载的是老目录时，就会「脚本 1.11.6、扩展 1.11.2」。现在构建脚本每次先删老目录，`dist/` 下只留 `extension/` 一份；manifest 的版本照旧从 `@version` 生成，弹窗与「关于」面板都读 manifest，三处不会走偏。

诊断面板的「标签写法」也顺手升级：能区分「中文界面 / 原始参数名 / 普通写法」，段头带「引用」前缀时额外标一句。

验证：`node --check`、sites 16 站、parse 61 条、version 16 条、extension 自检全过；`build-gf` / `build-ext` 重新出包，扩展目录只有一份且版本 = 1.12.0。

## v1.11.5

点卡片上的「原文」会把页面撑宽到几千像素，右边内容全跑到屏幕外。

内嵌时卡片活在站点的表格行里，而表格的列宽由「内容的最小宽度」决定。原文里只要有一行超长的编码参数（x265 的 `Encoding settings` 那行能有一千多字符），`<pre>` 就把整张表顶宽 —— hdwing 上实测表格从 **1058px → 5514px**，整页宽度 1600 → 5522。`overflow:auto` 拦不住这件事：滚动容器的最小宽度照样由内容决定。

改法分两层：

1. 兜底：`.mi-raw` 改成 `white-space: pre-wrap` + `overflow-wrap: anywhere` + `width/max-width: 100%`，任何浏览器上都不会再撑宽（代价是超长行折行、列对齐会散）
2. 能用的浏览器上更好：`@supports (contain: inline-size)` 里用 `contain: inline-size` —— 这一块的宽度不再由内容决定，于是**保留 MediaInfo 原来的列对齐**，超长行在框内横向滚动
3. 内嵌时原文框从固定 210px 改成 `min(52vh, 520px)`：整页本来就要竖着滚，一次能多看二十来行

顺带修掉一个连带问题：**重新扫描会把卡片自己的文字当成原文读回去**。点开「原文」后卡片里也出现了 `General` / `File size` / `Disc Size`，`readText()` 读父级容器时把 `tr[data-mi-host]` 里的卡片一起读了进来，于是原文开头变成「MediaInfo 复制 原文 定位 悬浮 主题 · 自动 …」再接真正的原文。现在 `readText()` 先剔掉 `.mi-root` / `[data-mi-host]` / `.mi-fab` 再取文字，扫描器的 TreeWalker 也直接拒掉这几类节点。

验证：仿 hdwing 夹具塞进 1000+ 字符的 `Encoding settings`，点「原文」后 `document.scrollWidth` 仍 1600、表格仍 1058、卡片 911，`pre` 宽度 911 而 `scrollWidth` 5437（框内横滚）；点「重新扫描」后原文仍以「引用 / General」开头，不再混入卡片文字；悬浮模式下 392px 卡片同样不越界。`tests/extension.test.cjs` 增加 3 条 CSS 断言（兜底换行、contain 分支、内嵌高度），共 49 条。

## v1.11.4

字段与音视频都正常了，剩的是 v1.11.2 那处「空行」在部分页面上没生效。

hdwing（HDChina 瓷器）的「简介」格会把剧情简介放进 `height:0` / `max-height:0` 的容器里收起：文字还在 DOM 里，`computed display` 也正常，但一个像素都不显示。v1.11.2 是**按可见文字长度**判断「这一行是不是只剩标签」的，这段看不见的简介照样算进去 → 长度超阈值 → 整行不收，于是留一行 47px 的空壳（左边「简　介」、右边空白）。

改成**按实际渲染高度**判断：

1. `contentPainted(row)` 只看标签格以外的内容格，累加每个可见子节点**真正占到的像素高度**；被 `height:0` / `max-height:0` 裁掉的容器高度是 0，不再被当成「还有内容」
2. 内容格里还有能点的东西（展开 / 收起 / 剧照链接）时不收 —— 收掉整行就再也点不到了，宁可留着
3. 文字判断仍然保留，两者取「或」：只剩标签（≤8 字）或内容格渲染高度 ≤4px，都算空行
4. 诊断新增一行 `空行: 标签行仍可见（内容格渲染高度 Npx）`，以后遇到同类页面能直接看出是「没判定成空行」还是「被别的内容挡住了」

验证：仿 hdwing 夹具加一份「简介被 `max-height:0` 收起」的变体，v1.11.3 下原行 `display:table-row` 留 28px 空壳（与用户诊断里的 47px 一致），v1.11.4 下 `display:none`，切悬浮后恢复 28px 且原文可见，切回内嵌重新收起；另用「简介真的显示」与「同行有剧照」两个变体确认不会误收。

## v1.11.3

原盘碟报解析不出音视频：**BDInfo 0.8.x（ffprobe 后端）换了一套更短的导出格式**。

老版 BDInfo 导出的是列对齐表格（`Codec  Bitrate  Description` 表头 + `MPEG-4 AVC Video  0 kbps  1080p / 23.976 fps / 16:9 / High Profile 4.1`），解析器按「2 个以上空格分列」。0.8.0.1 改成每行用「 / 」串属性、没有两连空格：

```
VIDEO:
MPEG-4 AVC Video / 1920x1080 / High
AUDIO:
DTS / 5.1 / 6 channels
DTS-HD MA / 5.1 / 6 channels
...
SUBTITLES: PGS × 32
```

这种行 `bdCols()` 只能切出 1 列，于是整段被丢掉 —— 卡片上就是 `视频(0) / 音频(0)`、分辨率空着、字幕只剩一条 `SUP`。这次：

1. **段内单列但含 `/` 的行按斜杠拆**（沿用 `bdSplitSlash()`，括号里的斜杠不拆）；列对齐的老格式走原路，不受影响
2. **段头带值的写法** `SUBTITLES: PGS × 32` 单独收。以前它既不是纯段头、又分不出两列，整行被当垃圾丢掉
3. **视频认 profile 名**：简写第三段只有 `High` / `Main` / `Baseline`，以前不匹配 `profile` 关键词就丢，视频行只有 `H.264`
4. **字幕支持计数**：`PGS × 32` → `SUP × 32`（老格式仍是逐条列语言与编码）
5. **`DTS-HD MA` 不再被归成 `DTS`**：ffprobe 版写的是 `DTS-HD MA`，原来只认 `DTS-HD Master`
6. **音频不去重**：一张盘常有好几条同规格不同语言的音轨（这份就有 9 条），之前为防重复加的 `uniq()` 会并成 3 条；只保留字幕去重（`SUBTITLES: PGS × 32` 同时被 `Key: value` 与分段表收到）
7. **同一张碟被父 / 子容器各认一次时合并**：BDInfo 没有文件名，`mergeSameFile()` 认不出同源，诊断里就是「识别份数 2」、卡片上多出 1/2 两份一样的内容。现在原盘用 `Disc Title` / `Disc Label` 当钥匙合并；没有碟名的不合并，免得把两张无标题的碟并成一份

顺带说明：这一版之后，「帧率」在原盘仍可能空着 —— ffprobe 版 BDInfo 不导出帧率，源里没有就不编。

验证：`tests/parse.test.cjs` 增加 16 条（老格式 5 条回归 + 简写 11 条），用 hdwing 这份实际贴文钉死碟名、正片 / 整盘体积、时长 `1h 43min 36s`、总码率 `43.71 Mbps`、分辨率 `1920x1080`、视频 `H.264 · High`、9 条音轨、`SUP × 32`、帧率留空；Chrome for Testing 在仿 hdwing 结构夹具上渲染，卡片 9 行字段、音频 9 条、字幕 `SUP × 32`，原「简介」行按预期收起。

## v1.11.2

从 hdwing（HDChina 瓷器）的实际诊断里捡出来的三处收尾。

1. **原文收起后不再留一行空的「简　介」**。`applySourceReplace()` 原来只对「站点自带面板」做「这一行只剩标签就整行收起」，纯原文（`fieldset` / `div`）收起后，表格里会剩下一行 47px 高的空壳：标签格还在，内容格一片空白，看着像报错。现在原文收起后同样判断一次：该行可见文字只剩标签（≤8 字）就整行收起；行里还有别的可见内容（截图、中文简介、其他说明）就不动，宁可留着也不误伤。
2. **诊断补一行「卡片」**。以前只有「解析结果」，分不清「没解析出来」和「解析出来了但卡片没显示」。现在第一屏直接给 `卡片: 已渲染 10 行字段 / 911×285`；高度为 0 会注明「多半被父级裁掉，或落在被收起的面板里」，卡片根本不在 DOM 里则写「渲染失败」。
3. **「整页标签兜底」先规范标签再匹配**。这一行扫的是整页原文，V1.11.1 只在候选文本和 `scoreMediaInfo()` 里做了 `deRawNames()`，兜底没做，于是在原始参数名页面上永远输出「有 Complete name=false / 有 File size=false」，把排查方向带偏（实际解析是好的）。现在兜底文本先过一遍 `deRawNames()`；顺带把体积值尾部的非数值内容裁掉（`3.20 GB制作组：CMCT` → `3.20 GB`），诊断里不再出现半截脏值。

验证：用 Chrome for Testing 跑一个仿 hdwing 详情页夹具（`table_details` 两列、中文简介单独一行、`#kdescr > fieldset` 放原始参数名 MediaInfo）：卡片渲染 10 行字段 `911×285`，`3.20 GiB` / `2015-03-08` / `x264 @ 3878 Kbps` / `DD 5.1 @ 640 Kbps` / 3 条字幕齐全；原来那行变成 `display:none`（0px），点「切换悬浮 / 内嵌」后恢复成 1843px 且原文可见，再切回内嵌重新收起。同一夹具上诊断输出 `有 Complete name=true / 有 File size=true`，与 v1.11.1 的 `false / false` 对比确认修复。

## v1.11.1

两个来自实际页面的问题：**卡片整块不出**、**诊断信息复制不出来**。

1. **认「原始参数名」写法的 MediaInfo**。有一类贴文贴的不是 `Complete name : …`，而是 MediaInfo 的内部参数名（`-f` / 原始参数名导出）：`CompleteName`、`FileSize/String`、`Format_Version`、`Channel(s)/String`、`Encoded_Library_Settings` …… 标签里没有空格。脚本原来的字段匹配全按带空格的写法做，于是这种贴文只有 `General` 段头能认出来 —— 得分停在 5 分（候选门槛 6），落选，最后就是「识别份数 0、页面不出卡片」。现在新增 `deRawNames()`：逐行把标签侧改写成普通写法（`CompleteName → Complete Name`、`FileSize/String → File Size`、`_` 当下划线分隔、camelCase 拆词、`/String` `/String3` 后缀去掉），取值一律不动。
   - `Format/Info`、`CodecID/Info` 这类「上一行的解释」整行丢弃，否则 `Format` 会被顶成 `Advanced Video Codec`；
   - `Channel(s)/String` 去掉后缀后仍是 `Channel(s)`，音频声道、字幕的字段匹配照旧；
   - 两个语义改名：`Encoded_Library_Settings → Encoding settings`（x264 命令行就在这一行，否则「参数」整行空白）、`Encoded_Library → Writing library`（「视频」认出 x264 / x265）；
   - 只处理「标签里带 `_` 或 `/`、或至少两段 camelCase 且紧跟冒号」的行，普通文本原样返回，可重复调用（幂等）。`normalizeText()` 与 `scoreMediaInfo()` 都会先过一遍，所以候选打分和后续解析用的是同一份规范化文本；
   - 顺带修 `fmtDuration()`：原始参数名导出的时长是 `1h 40mn`，原来的 `min` 规则认不出 `mn`，时长只剩 `1h`。
2. **「复制诊断信息」不再谎报成功**。原来只走 `navigator.clipboard` 与 `execCommand('copy')` 两条路，而它们都要求「页面有焦点 + 用户手势」；从油猴菜单点进来时焦点在扩展菜单上，两条路一起被浏览器拦下，代码却照样弹「诊断信息已复制到剪贴板」，粘出来是空的。

   - 其余两条按**真实返回值**回调，全失败时不再假装成功，而是弹出面板：完整诊断文本放只读文本框并已全选，点「复制全部」或直接按 ⌘C / Ctrl+C 都能拿到；
   - 复制成功时改用页面底部轻提示（`.mi-toast`），不再用 `alert` —— 原来的 `alert` 会把 600 字之后的诊断截掉，长文本根本看不全；
   - 卡片里的「复制」（整理文本）与「关于」面板的「复制诊断信息」共用同一套逻辑；
   - 诊断里新增「标签写法」一行（原始参数名 / 普通写法），下次再有类似贴文，一眼能看出是不是这个原因；
   - Chrome 扩展侧补 `clipboardWrite` 权限（`execCommand` 兜底要用），其余不变。

验证：新增 `tests/parse.test.cjs`（24 条，CI 会跑），用一份实际的原始参数名贴文钉死文件名 / 体积 / 日期 / 时长 / 分辨率 / 视频 / 音频 / 字幕 / 参数，并回归普通写法、幂等性与「纯中文简介不被误改」。真机侧用 Chrome for Testing 在一个仿详情页夹具（`#kdescr` + 两个引用框，一份 CMCT 中文简介 + 一份原始参数名 MediaInfo）上对比：旧版 `0` 个卡片节点，新版正常渲染出 `x264 @ 3878 Kbps` / `3.20 GiB` 等全部字段；再用 CDP 真点一次「复制诊断信息」，剪贴板被拦时面板照预期出现且文本已全选，可复制时改为底部轻提示。
